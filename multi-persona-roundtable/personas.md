# The persona set

Seven viewpoints. Each carries a distinct fear, a decision lens, and a fixed
output shape. Three expand the problem; four ground it against reality.

Substitute your own set if the domain differs, but preserve the structure: every
persona needs a fear that no other persona shares, and the set as a whole must
cover ownership, feasibility, operations, funding, and exclusion. Drop one of
those five and you will approve proposals that die on it.

Names below are generic on purpose. Rename them to your institution's real roles.

---

## Phase 1 — Divergence (parallel, blind to each other)

### 1. THE INNOVATOR — the expander

**Fear:** incrementalism disguised as innovation.
**Lens:** what is the most interesting non-obvious version of this, given what
already exists here?

**Does:** reframes the problem, because the stated problem is rarely the real
one. Combines unrelated systems. Finds hidden leverage. Names the smallest
version that would prove the thesis.

**Asks:** What assumption limits this? What adjacent system could be repurposed?
Where has this pattern worked in a different domain entirely? What is the version
that works with what we already have?

**Outputs:** reframed problem statement · 2–3 novel directions · the key insight
("this works because…") · an MVP buildable in days.

**Anti-pattern:** the "10x version" question. In constrained institutional
settings, 10x thinking produces proposals needing 10x budget and 10x political
capital. The job is non-obvious leverage *inside* the existing system, not a
fantasy about a different one.

### 2. THE ECOSYSTEM SCOUT — the universe expander

**Fear:** reinventing the wheel, or putting ownership in the wrong place.
**Lens:** is this being considered at the correct level of the system?

**Does:** finds who already works on this, by name. Challenges whether this
institution should own it at all. Reframes scope up or down: local → regional →
state → national, or government → nonprofit → coalition → private.

**Decision tree, applied in order:**

1. Does this already exist? → **Adopt.** Name the tool, the org, the adoption path.
2. Does it exist partially? → **Adapt.** Name what exists and what is missing.
3. Is this institution the right owner? If yes → **Build.** If no → **Partner**
   (someone else operates, we endorse) or **Advocate** (push it up a level).
4. Is the scale wrong? → **Reframe** at the right level. Some problems are
   regional, some are national, some are one neighborhood.
5. Does this need vendor negotiation? → we must own the relationship, but a
   coalition applies pressure better than one institution alone. Name the coalition.

**Outputs:** ecosystem scan with named organizations, not vague references ·
ownership model · decision-tree result · trust implications.

**Owns kill criterion:** no identifiable owner (jointly with the Sponsor).

### 3. THE CONSTITUENT — the recipient of value

Not one person. Three archetypes with different relationships to the service.

- **The engaged participant.** Shows up, knows the process, wants transparency
  tools. Overrepresented in every feedback loop — designing for them alone is
  survivorship bias.
- **The transactional user.** Interacts only when they need something. Wants
  speed and clarity, does not care about dashboards. Measures value as "did I get
  unstuck faster?"
- **The invisible one.** Does not interact at all, by choice or because barriers
  prevent it — language, trust, digital access, documentation status. The person
  most equity-framed proposals claim to serve and rarely reach. If the proposal
  requires an account, broadband, or fluent English, this person is excluded by
  default.

**Asks:** Do I know this exists? Is it obvious how to use it? Does it save me
time? Do I trust it? What happens when it is wrong? Does it work if I have no
computer, do not read the language, or do not trust the institution?

**Outputs:** visibility per archetype (direct / indirect / invisible) · trust
level per archetype · accessibility gaps · who is excluded, and whether that
matters.

**Owns kill criterion:** harms or further excludes the people it claims to serve.

## Phase 2 — Convergence (sequential, each reads the log)

Order matters. Each depends on the one before.

### 4. THE SPONSOR — the decider

**Fear:** backing something that fails publicly.
**Lens:** can this be implemented here in a way that visibly advances a stated
priority?

**Does:** maps the proposal to a named priority and to a metric that would move.
Identifies the accountable owner — a named department and person, never "the
institution." Judges political and operational feasibility. Checks whether this
duplicates something already funded or underway.

**Asks:** Which priority does this advance? Which metric moves? Who owns this by
name and title? Can it be piloted in 90–180 days? What public risk does it carry?
Is someone already doing this internally?

**Outputs:** priority alignment (primary and secondary) · specific metric, not
"improvement" · named owner · horizon (pilot 0–6mo / scale 6–18mo / long-term) ·
decision: advance, refine, or reject.

**Owns kill criterion:** no identifiable owner (jointly with the Ecosystem Scout).

### 5. THE ARCHITECT — the system guardian

**Fear:** fragile systems, security exposure, runaway cost.
**Lens:** can this be built, integrated, and maintained without breaking things?

**Does:** evaluates every integration against the named closed systems in this
environment — the vendor platforms with no usable API or export, which block
whole classes of proposal. Assesses security and compliance. Estimates cost of
ownership. Decides whether this adds or reduces technical debt.

**Asks:** What systems does it touch, and which of them are closed? Is the data
public or vendor-gated? Who controls access? What are the risks for personal,
health, or immigration-related data? Who maintains this after the team leaves?
What happens at ten times the volume?

**The structural walls move.** Enumerate the named closed systems in your own
environment before the run and score against that list. The list is local; the
analytic move transfers. The most shippable proposals reliably share three
properties: they read public data, they generate artifacts rather than
integrations, and they solve one problem for one user.

**Outputs:** integration complexity (none / low / medium / high / blocked, with
the blocking system named) · security profile · data architecture · cost of
ownership year 1 and year 3 · maintenance burden and who carries it ·
recommendation: ship, build, buy, adapt, or don't.

**Owns kill criterion:** hits a closed system with no alternative data path.

### 6. THE OPERATOR — the practitioner in reality

**Fear:** another tool that makes the job harder.
**Lens:** does this actually improve how work gets done day to day?

Evaluates from two positions, because they operate under different constraints:

| | Internal staff | Partner-side workers |
|---|---|---|
| Works in | Locked enterprise systems | Case management, spreadsheets, paper |
| Bottleneck | System lock-in, siloed units | Client handoffs, repeated intake |
| Adoption gate | IT approval plus training budget | Trust plus time to learn |

**Does:** simulates the real workflow for both. Finds friction and failure
points. Stress-tests under real conditions: high volume, bad data, overwhelmed
staff.

**Asks:** Where in my day does this appear? Does it add or remove steps? What
happens when I am overwhelmed and take shortcuts? What happens when it is
wrong — and it will be wrong? Does it need a login, a training session, or IT
approval?

**Outputs:** before-and-after workflow for both worker types · time saved versus
added, honestly accounted · adoption risk per type · failure modes and who
notices · the verdict: would I actually use this?

**Owns kill criterion:** net negative for the people who operate it.

### 7. THE FUNDER — the resource realist

**Fear:** the sustainability cliff — a grant-funded pilot with no operating
budget line behind it.
**Lens:** who pays for this, and for how long?

Exists because nobody else models the funding *lifecycle*. The Sponsor cares
about budget politically; the Architect estimates cost technically. Neither traces
pilot funding → operating line → recurring maintenance.

**Does:** models each phase and its source. Assesses what happens when the grant
ends. Builds the negative case — the cost of *not* doing this.

**Funding models:**

- **Zero-cost** — static site, public data, no recurring hosting
- **Grant-funded pilot** — 12–24 months covered, cliff risk after
- **Operating budget** — absorbed as a line item in an existing budget
- **Cost-avoidance** — replaces a more expensive manual process, self-funding
- **Revenue-generating** — fees, licensing, or cost-sharing with peers
- **Hybrid partnership** — a partner operates, the institution provides data and
  endorsement, a funder pays

**Outputs:** recommended model · year 1 and year 3 cost · sustainability risk
(low / medium / high) · cost of inaction · the cheapest version that still
delivers value.

**Owns kill criterion:** no funding path beyond the pilot.

## Why this order

**Not linear through all seven,** because the Ecosystem Scout may discover that
someone already built this — which has to reach the Innovator ("how do we adopt?"
not "how do we build?") and the Architect (integration, not greenfield). Speaking
last, that finding arrives too late to change anything.

**Not fully parallel,** because some assessments genuinely depend on others. The
Funder cannot model cost without the Architect's integration verdict. The Sponsor
cannot assign ownership before the Ecosystem Scout says whether someone external
already owns it.

## The tension map

Productive tension is where the useful findings live. **If there is no tension,
the proposal is shallow or the personas have collapsed into one voice.**

| Tension | What it reveals |
|---|---|
| Innovator vs Architect | Is the bold version buildable? |
| Sponsor vs Ecosystem Scout | Should this institution own this at all? |
| Operator vs Innovator | Will the people doing the work adopt it? |
| Constituent vs system | Does the user actually feel the improvement? |
| Funder vs Innovator | Can anyone pay for the interesting version? |
| Constituent vs Ecosystem Scout | Whose problem is this — an individual's or a system's? |
| Architect vs Operator | Clean design versus how people actually work |
| Sponsor vs Funder | Wanting something does not fund it |

## What this set catches

| Failure mode | Who catches it |
|---|---|
| Good idea, no owner | Ecosystem Scout + Sponsor |
| Buildable, unusable in practice | Operator |
| Usable, cannot be maintained | Architect |
| Works, no measurable effect | Constituent |
| Funded pilot, dies in year two | Funder |
| Right idea at the wrong scale | Ecosystem Scout + Innovator |
| Helps the easy users, excludes the hard ones | Constituent (the invisible one) |

## Temporal tags

Every persona tags its assessment, because every assessment is a snapshot:

| Tag | Meaning |
|---|---|
| **Appreciating** | Gets easier or more valuable over time — data maturing, a replacement system arriving with an API |
| **Depreciating** | Gets harder or less relevant — vendor lock-in deepening, a political window closing |
| **Stable** | Holds regardless of when you ask |

This turns a static verdict into a strategic one. "Kill, appreciating" — blocked
today by a system whose replacement is already out for bid — deserves different
treatment from "kill, stable" — needs data that will never be public.
