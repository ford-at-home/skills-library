# Six ways a statement set fails after it looks finished

Each of these ships a statement that reads as well-scoped and grounded. That is
why the corresponding rules in SKILL.md are rules and not preferences — the
defect surfaces at the event, in front of the participants, and not in review.

**The one it exists to catch.** A statement names a dataset that everyone assumes
is public. Teams arrive, discover the system has no API and the export is
quarterly, and spend the weekend building against invented data. Gate 3 needs all
three fields — owner, access path, cadence — because "it's on the open data
portal" is true of a file last refreshed two years ago.

**Solution language creeping back in.** It re-enters during review, when someone
helpfully sharpens "residents cannot find services" into "build a service
finder." The statement then has exactly one acceptable answer and every
submission looks the same.

**Count by symmetry.** The plan has seven priorities so the program gets seven
pillars, one of which has no committee. That pillar's participants get no ally,
no data help, and the worst experience at the event.

**The open-ended escape hatch.** Statements that fail the data gate get relabeled
open-ended rather than fixed. Two cycles of this and the open-ended half of the
program is where unfalsifiable statements go to hide.

**Ally as department.** "Procurement" answers no email. A named person with a
recorded commitment does.

**Silent freeze violation.** A statement gets edited mid-event to match what a team
built. Every judgment made against the old wording is now unexplainable.
