# How submission scoring goes wrong

**The one it exists to catch.** A field's strongest demos cluster on a pattern
that is structurally blocked. In one pillar of the source run, four of five
submissions built document extractors against a closed content system with no
API, while the highest-tier ideas used only public tabular data that was clean,
complete, and refreshed monthly. Desirability ranked the extractors first;
survivability ranked them last. Averaging the two produces a mid-table result for
both groups and destroys the only actionable conclusion in the dataset.

**Demo-first reading.** You watch the demo, form a view, then read the statement
and score alignment to match. Writing the statement's requirements down first is
the only reliable defense, and it has to be *written*, not remembered.

**Polish halo.** Execution bleeds into impact and user value. A working prototype
of the wrong thing scores as a working prototype.

**Optimistic data readiness.** A source scores 5 because it "should" be public.
The band requires a confirmed endpoint and a recent update, not a reasonable
expectation.

**Double-counting a defect.** A submission gets `SYNTHETIC_DATA` and also loses
two points on feasibility for the same reason. The penalty is now invisible and
unrepeatable.

**Stale cached totals.** A spreadsheet's summary column was computed before three
scores were corrected. It looks authoritative because it is a number in a cell.

**Silent drops.** Submissions with no second evaluation vanish from the output
rather than rendering as human-only. Nobody notices until someone counts rows.
